# iOS 16 on the Joy Tab 2 (MT8766, 4x Cortex-A53): the 4K-page question

Research notes, 2026-10-20 (branch a53-4k). Sources: XNU xnu-8796.141.3 (the iOS 16.6/16.7 generation) and
dipa-studio/ios-sweet (iOS 16.7 userland + XNU on Redmi Note 10 Pro).

## Why it matters
Cortex-A53 implements only the 4K and 64K translation granules. iOS 16 kernels run with 16K pages, and
ios-topaz (Redmi Note 12 4G) parks its A53 cores for that reason. The MT8766 has nothing but A53s.

## XNU still supports a pure 4K kernel
- `osfmk/arm64/proc_reg.h`: without `__ARM_16K_PG__`, ARM_PGSHIFT = 12 and TCR TG0/TG1 = 4KB.
- `osfmk/mach/arm/vm_param.h`: arm64 kernel PAGE_SHIFT comes from runtime `PAGE_SHIFT_CONST`;
  userland PAGE_SIZE = `vm_page_size` (runtime), PAGE_MIN_SIZE 4K, PAGE_MAX_SIZE 16K.
- `osfmk/arm/pmap/pmap_data.h`: PT_INDEX_MAX has an `ARM_PGSHIFT == 12` case (4 page tables per VM page).
- `osfmk/arm/pmap/pmap.c` ~10990: "Ensure that 64-bit devices using 4K pages can nest the commpage
  completely above the maximum userspace VA": a maintained pure-4K configuration, separate from
  `__ARM_MIXED_PAGE_SIZE__` (Rosetta-style 4K user pmaps on a 16K kernel).
- Likely why: tvOS 16/17 still supported Apple TV HD (A8, 4K pages), so this generation shipped 4K builds.
  Inference, not verified against a tvOS kernelcache.
- Only the H13 (M1) and VMAPPLE board configs are public; both define `__ARM_16K_PG__`. ios-sweet's
  `0004-sweet-machine-config.patch` defines it too (line ~250), modeled on VMAPPLE.

## Userland signals
- ios-sweet NOTES (patch 0035): "ALL iOS 16 binaries (launchd, backboardd, SpringBoard) use 4K code
  pages": code signatures hash 4K pages; a 16K kernel converts them (ubc_cs_convert_to_multilevel_hash).
- Mach-O segments and the shared cache are 16K-aligned, which is also 4K-aligned.
- ISA: ios-topaz runs the same userland on Cortex-A73 (ARMv8.0), so ARMv8.2 features are not required.
- Unknown: hard-coded 16K assumptions in iOS 16 frameworks or daemons (A11-only build). Needs a test.

## Joy Tab specifics
- GICv3 (`arm,gic-v3` @ 0x0c000000), same as sweet: their interrupt code fits.
- A53 errata: the tablet's own TF-A log (backup/expdb.bin) says
  "cortex_a53: errata workaround for 835769 was missing" and "... 843419 was missing", i.e. this CPU revision
  is affected by both. Those are fixed only at compile/link time (-mfix-cortex-a53-835769,
  --fix-cortex-a53-843419). Apple never shipped A53 cores, so iOS binaries are not built with the fixes:
  expect rare, silent miscomputation or bad loads in Apple code. Not fixable without rewriting binaries.
- Drivers to write for XNU (ios-sweet did the Qualcomm equivalents): MSDC eMMC, MTK display/framebuffer
  handoff, MT6357 PMIC via pwrap, GT912 flashless touch (our loader protocol), keys. ~65 patches on sweet.

## Cheapest real test
1. Fork ios-sweet; build its XNU on GitHub macOS runners with `__ARM_16K_PG__` removed from the sweet config.
2. Fix what breaks: their shim, ADT and physmap patches assume 16K (e.g. NOTES 0011 slide math, 0024 memdev).
3. Boot it in QEMU `virt`, `-cpu cortex-a53` (their tools/qemu-sweet.py uses cortex-a76), first to the RAM-disk
   init, then to launchd from the iPhone X 16.7 root (user supplies the IPSW; Apple licenses iOS for Apple
   hardware only).
Only if launchd and SpringBoard come up in QEMU on 4K would hardware work on the Joy Tab make sense.

## Update: Apple ships a Cortex-A53 4K config
xnu-8796 itself contains `pexpert/pexpert/arm64/BCM2837.h` (Raspberry Pi 3, 4x Cortex-A53) in
SUPPORTED_ARM64_MACHINE_CONFIGS: no `__ARM_16K_PG__`, `__ARM64_PMAP_SUBPAGE_L1__ 1`. A 4K-page XNU on A53
is a configuration Apple keeps in this exact tree.

## This branch
`xnu/patches/0099-a53-4k-pages-armv8.0.patch` (applied last) turns the SWEET config into an A53 one:
4K pages with subpage L1 tables like BCM2837, no PAN (ARMv8.1), `-march=armv8-a+crypto` (no LSE atomics)
and `-mfix-cortex-a53-835769`. Run the xnu workflow on this branch, then boot in QEMU with
`tools/qemu-sweet.py --cpu cortex-a53`.

## Results (QEMU virt, -cpu cortex-a53, 4K pages)
Control: upstream's 16K kernel boots on cortex-a76 but faults at MMU-on on cortex-a53 (instruction abort at
the kernel's physical entry), so QEMU enforces the missing 16K granule.

Fixes needed in patch 0099, found boot by boot:
1. Pages: no `__ARM_16K_PG__`, subpage L1 (BCM2837-style); no PAN.
2. iOS user VA max 0xFC0000000 so the 4K commpage nests (pmap static_assert).
3. iOS kernel layout (no ARM_LARGE_MEMORY, link 0xfffffff007004000): 4K 3-level tables give TTBR1
   only 38 bits; the macOS -2TB layout took a level 0 translation fault at the kernel VA.
4. Splash framebuffer bootstrap mapping found through its L1 entry, enough 2MB blocks for 12MB.
5. `-mcpu=cortex-a53` (not only -march): the macOS target kept Apple-CPU LSE atomics (ldadd trap).
6. ARMv8.0 ldaxr/stxr fallback for the commpage PFZ trylock (casa).
7. Final framebuffer alias below gVirtBase in 2MB blocks (no table at VM_MIN_KERNEL_ADDRESS with 4K).
8. libfirehose_kernel's arm64 slice built with the A53 flags (CI workflow).
9. iOS zone map sizes (macOS reserves 128GB of VA, more than the ~112GB iOS kernel map).

Build 8 (run 39622379233): Darwin 22.6.0 / xnu-8796.141.3 boots through VM bootstrap, CPU init, BSD init,
MAC policies (SWEET AMFI, Sandbox), AppleCLCD, HFS, mbufs and networking, then panics in IOFindBSDRoot
because no RAM disk was attached (`rd=md0`). The 4K kernel side works on Cortex-A53 in QEMU.
Not covered by QEMU: Cortex-A53 errata 835769/843419 in Apple's userland binaries.

RAM-disk test init (same kernel): `tools/sweet-init.S` preprocessed with cpp and assembled with
`llvm-mc -triple arm64-apple-ios16.0` (no Apple toolchain needed), wrapped by `tools/mkinit.py`, attached
with `mkpayload.py --ramdisk` and `rd=md0` (mockfs serves it as /sbin/launchd). On QEMU cortex-a53, 90 s:
`BSD root: md0` -> `load_init_program: attempting to load /sbin/launchd` ->
`*** SWEET userspace: init running as PID 1 ***` -> `SWEET init: still alive` every 5 s, no panic.
So 4K-page userland exec, ad-hoc code signatures, syscalls, devfs and timers work on Cortex-A53.

Disk root for QEMU: the iOS root (16 GB HFS+) does not fit a RAM disk on the build host, and QEMU has no
UFS host, so `bsd/dev/sweet_vblk.c` (in patch 0099) is a polled virtio-mmio (version 2) block driver,
exposed like sweet_ufs.c's ufsroot0 as vblk0/rvblk0 (`rd=vblk0`); `tools/qemu-sweet.py --disk IMG`
attaches it. Build 9 with an empty 64 MB journaled HFS+ image: `SWEET VBLK: vblk0 64 MiB, read-write`
-> `BSD root: vblk0` -> `hfs: mounted VblkTest on device b(1, 0)` (journal initialized, so writes work)
-> panic exec /sbin/launchd (empty volume), as expected.

iOS root: `tools/mkiosroot.sh` needs an apfs-fuse with LZBITMAP support (Fedora's 2020 snapshot fails
~138,800 files with EIO; current sgan81/apfs-fuse built from source reads them all). 23 localized Shortcuts
example names stay "illegal" for the Linux fsck port; harmless for booting.

With 16K VM pages on the 4K MMU (XNU uses PAGE_RATIO 4 when RAM > 1GB), pmap_create_commpages picked a
random commpage text VA that is only 4K-aligned and write_pte_fast panicked about 3 boots in 4; patch 0099
rounds it to a VM page. Backtraces: `qemu-sweet.py --stack-words N` + `tools/xnu-backtrace.py`.

Build 10 (run 39631977409), iOS 16.7.16 root on vblk0, upstream boot-args with rd=vblk0, QEMU cortex-a53,
5 minutes: no panic, the screen shows the Apple logo with a boot progress bar (~25%), drawn by userspace
(kernel progress is off with -noprogress): launchd and system daemons are running on 4K pages.
